# Dual-GPU tuning results, 2026-08-16

Hardware: RX 7900 XTX (gfx1100, 24 GiB, **also drives the desktop**) + AI PRO
R9700 (gfx1201, 32 GiB). llama.cpp pinned at b10358.

## Shipped configurations

All measured on one harness: 6.2k-token uncached prefill, 256-token decode at
~10k context depth, Pi's real sampling params (temp 0.6 / top_p 0.95 / top_k 20)
with a fixed seed. f16 KV throughout.

**Two models lead, and they are close**: Qwen3.6 35B-A3B (3128 pp / 94.4 tg) and
Nemotron 3.5 (3034 pp / 94.6 tg). Both are ~3B-active MoEs, so they read far fewer
bytes per token than the dense 27/30B models, that is the whole story of this
table. Nemotron additionally offers 1M context at no decode cost; Qwen3.6 has
vision and working speculation. Everything dense sits at 33-39 t/s.

## Findings that generalise

**f16 KV everywhere.** Not a space/speed tradeoff, it raises *speculative
acceptance*, because a quantized KV makes drafter and target disagree more often.
Muse: 43.6 → 58.5% acceptance, +19% decode. Qwen3.8 at a fixed split: +11% decode,
+7.4 points. Only drop to q8_0 where f16 genuinely will not fit.

**Tensor-split is not a property of the model.** It depends on what else is
resident on the XTX. The 35B shipped at `ts 18,22` early in the session; when the
desktop grew from ~1.7 to ~3.0 GiB that same config began *timing out*, and
re-splitting to `16,24` made it 24% faster on prefill. Re-check splits whenever
the desktop footprint changes.

**Both cards are constrained.** Protecting the XTX by pushing layers onto the
R9700 has its own ceiling: `ts 14,26` on the 35B leaves the R9700 with 44 MiB
free, and `ts 26,39` on Qwen3.8 leaves it 96% full. Balance, do not just shift.

**Draft depth does not transfer** between models, backends, or topologies.
Muse wants n-max 2 on both backends here; upstream documentation and this repo's
own archived note both say 15, which measures *worst* (6.5% acceptance), that
note was for the Q5_K_M on a **single** GPU. Spanning two cards makes the verify
pass expensive and favours shallow drafts.

**Large batch is ROCm-only.** batch 6144–12288 is worth +13% prefill on ROCm and
is a measured no-op on Vulkan, confirmed on three separate models.

**Rank with multiple SEEDS, not repeats.** The harness fixes the seed, so
repeating a config reproduces the same number (0.1–0.5% spread) and cannot
distinguish a real effect from one lucky seed. Qwen3.8 `ts 28,37` measured 29.23
tg on one seed and 29.1–40.8 (median 38.5) across five, it was nearly rejected on
the strength of a single unlucky sample.

## Bugs found and fixed

- `common.sh` defaulted `LLAMA_DFLASH_SPEC_TYPE` to `dflash`; this build requires
  `draft-dflash`. Any DFlash profile using the default failed to start. **Fixed.**
- `common.sh` emitted `--spec-draft-type-k/v` only on the mtp path, so a DFlash
  drafter's KV precision was unreachable from a profile. **Fixed.**
- `LLAMA_TIMEOUT` defaulted to 0 = a ZERO-second socket timeout. Large bodies died
  with an empty 400 and nothing logged; 4K images succeeded 3/8 of the time.
  **Fixed** in `default.sh` and every profile.
- Launcher referenced 4 deleted models and 2 deleted DFlash sidecars. **Fixed.**

## Open problems

- **Nemotron 3.5: MTP hangs ~37% of generations, RESOLVED by disabling it.**
  With `--spec-type draft-mtp`, 3 of 8 generations never returned (reproduced at
  256 and 512 tokens, at 256k and 1M context, with both q8_0 and f16 KV). With
  speculation off: 8/8 at 96.1-96.5 t/s, and *faster* than the MTP runs that did
  complete. Both Nemotron profiles ship with `LLAMA_SPEC_MODE=none`. The
  underlying bug is still upstream's, worth re-testing on b10450, which contains
  `#26623 recurrent state rollback for ggml_ssm_scan`.
- **Prompt-cache restore crashes.** One hard crash during testing:
  `ROCm error: an illegal memory access` inside
  `server_prompt_cache::load → llama_context::state_seq_set_data`. Intermittent,
  a control run with the cache enabled completed fine. Cache left ON because the
  reprocess problem it solves occurred 8x in one session versus this once.
- **Post-image prefill regression.** One image costs ~31–40% of prefill until
  restart. Ruled out: batching, thermals, mmproj device, prompt cache, GTT spill.
  Matches upstream issue #26873 (unverified).
- **b10450 is ~5% slower** than the pinned b10358 (`#26696` removed
  `-funsafe-math-optimizations`). A local one-line patch restoring it would give
  the newer server fixes at no cost, untested.
